Implementation take · charts first

Analytics charts for the SRA Don Pedro dashboard

The frozen Analytics Opportunity Mapping spec asks for five analytics opportunities. This board sorts every one of them by what the shipped Web app can actually draw today, then gives a three-phase build order. No advanced analytics, no forecasts, no rankings — and an explicit list of what stays out, with the frozen rule that keeps it out. All eight questions are decided — including the chart library, Recharts 3.10.1. The decisions and their effect on the plan are below.

What the Web app has today, and what is missing

Read from the code, not from the plan documents. The gap that decides the whole plan: there is one aggregate endpoint, and it is a UTC calendar month.

Already collected and already shown — keep, never repackage

  • Five operational queues — needs review, needs visit, follow-up due, upcoming, unverified-no-active-work (ApplyOperationalQueueFilter)
  • Calibrated attention bands — green/amber/red derived from reviewer verdicts with printed reasons, not an opaque score (CalibrateReportTriage)
  • Monthly summary — reported cases, estimated hectares, validation counts, closed cases, review-time stats, barangay and Possible Condition lists (BuildMonthlyReportSummary, MonthlyCaseSummary.tsx)
  • Expert verification — consult volume, agreement, unable-to-classify, time to finding, advisory coverage
  • Case register with custom date_from/date_to filters, CSV export, map with located/unlocated counts, visit calendar

The five gaps that shape the plan

  • One aggregate endpoint, UTC month only. No week, no custom range, no series, no previous-period comparison.
  • No chart component and no chart dependency. Today's “charts” are <ul> lists and <dl> definitions; the only inline SVG in the SPA is on the login page. The captain’s Q3 decision adds one library for this work — nothing exists to reuse.
  • The register is the wrong source. per_page caps at 100 and pages, so a browser-side chart would silently truncate.
  • Several stored dimensions are never aggregated — case_state, authority_classified_condition, workload per assignee, waiting-age buckets, turnaround durations.
  • The area total has no provenance and no overlap disclosure — a bare SUM(affected_area_hectares), no measured/not-measured split, no linked-duplicate count.
Demo data can lie. ReportSeeder seeds predicted_label from Report::v2Labels(), which includes smut, "so monitoring exercises every prediction class". Any chart built on the seeded database will show a Smut series that no shipped model produces. That is the exact trap the spec's current-vs-target rule (§3.2, §4.3) exists to prevent.

Needs data first  The Available Data rule (§3.3) fails today

Four items are blocked by a missing input; the fifth is blocked by where the data is allowed to live. Each card names the frozen rule and the exact input still missing.

N1 · Smut as an AI Possible Condition series

Missing input
A retrained, integrated and tested classifier that emits smut, with evaluation evidence (§27 lists dataset, balance, retraining and evaluation as outstanding).
Frozen rule
§4.3 / §3.2 — Model v0 integrates Healthy, Mosaic, Rust only; Smut “must not be presented as current Model v0 outputs until the model is retrained, integrated, and tested”.
Why it looks buildable
The upload contract can carry smut (mobile-report-upload-v2.json enum healthy|mosaic|rust|smut) and ReportSeeder deliberately seeds it. A Smut bar would chart seeded rows, not model output.
Verdict
Declare the condition list as healthy, mosaic, rust; add smut with the model integration, not with the data.

N2 · RSSI as an AI Possible Condition series

Missing input
Any rssi value in the prediction contract. It does not exist: predicted_label accepts healthy|mosaic|rust|smut, and Report::LABEL_* defines the same four. RSSI exists only as reporter_suspected_condition = 'RSSI' and as a Staff-Classified Condition.
Frozen rule
§4.2 / §3.2 — RSSI is in the five-category target; the current/target distinction must always be visible.
Why it is worse than N1
A “Possible Condition: RSSI” bar cannot be drawn without inventing a value. This is a stronger block than Smut, where at least the wire format exists.
Verdict
Two honest options: a clearly separate reporter-suspected RSSI count labelled as a Level-2 reporter observation, or wait for the five-category model. Never inside the Possible Condition chart.

N3 · AI-to-staff agreement at a useful volume

Missing input
Reviewed reports carrying authority_classified_condition. ReportSeeder writes none (status and lifecycle only); AdvisorDemoSeeder writes about eight. The real denominator is near zero.
Frozen rule
§13 agreement rule read with §3.3 — agreement uses usable staff classifications only, and Unable to Classify is excluded from the denominator (Q44).
Verdict
C10 ships in Phase 3 with a first-class insufficient-data state and the denominator always printed. It is not a Phase 1 chart and must never be headlined as a percentage alone.

N4 · Policy-target and SLA comparisons

Missing input
A policy date. Validation: target_visit_date is a real human-entered deadline and is usable where set — but it is nullable and only exists once an assignment is created, so coverage is unknown. Review: there is no stored review deadline anywhere, so “reviewed within N days” has no date to measure against.
Frozen rule
§11 “overdue only with a real deadline”; §25 “arbitrary thresholds/SLAs” out of scope.
Verdict
Measured turnaround (C12) and past-target validation (C8) are fine, with an explicit unscheduled bucket. A review-SLA chart waits for a policy decision, not for data — choosing N would be the invented threshold the spec forbids.

N5 · Readiness and synchronisation charts (Map 2) — wrong surface, by rule

Missing input
Nothing collectable. Incomplete, Ready for Submission, Finalized-Pending Synchronization and Synchronization Failed are device-local states; the office only ever receives Submitted.
Frozen rule
§17 “Office analytics only use synchronized data”; Q39 “unsynced stays mobile-local”.
Verdict
Not a data-collection gap — structurally impossible without breaking the frozen rule. This requirement belongs to the Mobile readiness surface. The Web dashboard may state only the Submitted count it already has.

Build order — three phases, charts first

Stance for all three, from the recorded decisions: one new runtime dependency — Recharts 3.10.1 (Q3, Q8) — and no schema change. That dependency sits in a chart-theme layer that reads colours and text sizes from src/styles/tokens.css, because npm run test:design-spine fails on literal hex, literal font-size and literal border-radius outside the token sheet. The period substrate belongs to the already-approved documents work (Q5): charts extend it rather than re-deriving PHT boundaries. Cost accepted with Q3: the printed document keeps its server-rendered SVG bars, so the SPA and the document are two renderers sharing one aggregate.

Chart engineering decisions

Small, concrete, and now including the one dependency the captain chose (Q3).

Library — Recharts 3.10.1 (Q8 decided)

MIT · declared React 19 peer · SVG output · a declarative API covering all thirteen shapes. Verified cost: 12 direct dependencies including @reduxjs/toolkit, react-redux and immer, ~7.5 MB unpacked — which is why the lockfile review and npm run security:dependency-check sit in the Phase 1 gate. @nivo/bar + @nivo/core 0.99.0 (MIT, React 19, SVG-first, 343 KB + 254 KB) is the named lighter substitute if that surface is refused later.

Rejected, with the facts

chart.js 4.5.1 and echarts 6.1.0 render to canvas — print fidelity, token theming and accessible output all suffer. react-apexcharts 2.1.1 declares SEE LICENSE IN LICENSE rather than MIT, and this project already runs licence reviews. victory 37.3.6 only declares react >=16.6.0, so it does not certify React 19.

Theming under the design spine

npm run test:design-spine fails on a literal hex colour, literal font-size and literal border-radius outside tokens.css — and a library does not exempt the components using it. Colours and text sizes are read from the tokens at runtime and passed as props: --disease-* for conditions, the --color-brand family for counts, warning/danger only for genuinely past-target buckets.

Accessibility

Each chart is role="img" with a summarising aria-label plus a visually hidden <table> of the plotted values. That hidden table is also what makes a chart testable without a browser. Chart text uses the project’s 16 px floor; the 12 px machine scale is never used for labels.

Honest empty states

Zero reports renders “No submitted reports in this period”, matching existing copy. A sparse denominator renders the insufficient-data state instead of a rate, and below an eligible denominator of 10 the agreement card shows counts only (Q4).

One printed period rule — Q1 decided

Charts use PHT (UTC+8) and print the period, the boundary rule and the timezone on every chart. The monthly panel stays UTC (Q6), so the divergence is now permanent and deliberate — the printed rule is what keeps the two readable side by side.

No client-side aggregation

The register endpoint caps at per_page=100 and paginates; charts read the aggregate endpoint only. One payload per period change, debounced — no per-chart request fan-out.

Copy contract

A single copy module beside the chart components holds the required disclaimers and the forbidden vocabulary from X1–X14, with tests asserting both. This is the mitigation for the spec’s central risk: charts that quietly become claims.

Two renderers, one aggregate

The library serves the SPA only. The printed document keeps its server-rendered SVG bars, so the shared aggregate — not shared rendering — is what keeps their numbers equal. This is the accepted cost of Q3, not an oversight.

Library decided — nothing open

Q3 approved a library and Q8 chose the package: Recharts 3.10.1. Versions, licences, React peer ranges and dependency counts below were read from the npm registry on 2026-09-22, not recalled. This section is a record, not a question.

Chosen — Recharts 3.10.1

  • MIT, declared React 19 peer range, SVG output, declarative React API covering all thirteen chart shapes.
  • Accepted cost: 12 direct dependencies including Redux Toolkit, react-redux and immer; ~7.5 MB unpacked. The lockfile review and npm run security:dependency-check in the Phase 1 gate are what keep that visible.
  • Named substitute: @nivo/bar + @nivo/core 0.99.0 — MIT, React 19 peer, SVG-first, 343 KB + 254 KB. Swapping it changes nothing else in the plan.
  • Scope: the SPA only. The printed document keeps its server-rendered SVG bars, so the two surfaces share the aggregate, not the renderer.

Rejected, with the facts

  • chart.js 4.5.1 and echarts 6.1.0 — render to canvas: print fidelity, token theming and accessible output all suffer.
  • react-apexcharts 2.1.1 — declares SEE LICENSE IN LICENSE rather than MIT, and this project already runs licence reviews (the documents plan flagged mPDF's GPL).
  • victory 37.3.6 — its peer range stops at react >=16.6.0, so it does not certify the React 19 this repo runs.
  • Recharts 2.15.4 and @visx 4.0.0 — viable, but the previous major line and a build-it-yourself primitive set respectively; neither beat the chosen option on the criteria that mattered.
