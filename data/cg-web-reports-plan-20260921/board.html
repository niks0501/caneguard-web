CaneGuard Web · plan for decision

Documented reports — weekly, monthly, and any date range

Today the system exports a CSV. This plan turns that data into a beautiful, branded, self-describing document that a municipal office can print, file, or hand to an authority — with the real document previewed on screen for whatever period was chosen, before anyone downloads anything.

The ask, restated

What "beautiful documented reports" means here

Three report shapes, one document template, a preview that shows the exact period chosen, and a generation flow measured in clicks. Everything below is grounded in what this repository already contains — the numbers in the next card are the ones the API computes today.

Weekly · monthly · custom

One code path, three period definitions. Weekly defaults to the last completed ISO week, monthly to the last completed month, custom takes an explicit from–to range capped at 366 days.

2 clicks for the common case

Open the builder, press Download PDF. The period defaults to the last completed week and the preview renders as you change it, so nothing needs a "generate" click just to look at.

One template, two outputs

The preview is the document — the same Blade view that Chromium prints to PDF. No parallel layout, no drift between what is reviewed and what is filed.

Research outcome

Winner and fallback

Six approaches were weighed on output beauty, CaneGuard brand fidelity, offline behaviour, dependency weight, and maintenance. Two compatibility facts were verified against Packagist metadata and this repository — they are shown below so the recommendation rests on evidence, not preference.

Winner

HTML → PDF via headless Chromium — spatie/laravel-pdf + Browsershot, rendering a server-side Blade document

  • Brand fidelity is the whole point. Only a real browser engine renders the CaneGuard design system — the tokens.css palette, Poppins, the 16 px text floor — plus flex, grid and print CSS. A pure-PHP builder would force every section to be re-authored as tables and floats; @react-pdf/renderer would force a second layout in its own primitive DSL.
  • The preview requirement is satisfied by construction. The same Blade document is the on-screen preview and the PDF source. What the captain approves is what gets filed.
  • Print quality that actually holds up. Chrome 131+ supports @page margin boxes with counter(page)/counter(pages) for real page footers, repeating thead across page breaks, and break-inside: avoid on metric cards. Honest limitation: Chromium does not support dynamic running headers (string-set) or CSS footnotes — this plan needs neither.
  • It fits the stack that already exists. The API already renders Blade and already ships a print-ready CaneGuard document (the referral summary). Node is already a documented staging host prerequisite in docs/staging.md.
  • Driver-swappable, MIT, Spatie-maintained. Moving to Gotenberg or WeasyPrint later is a LARAVEL_PDF_DRIVER change, not a template rewrite.

The honest cost: a ~300 MB Chromium binary, Puppeteer, and seconds (not milliseconds) per render at ~250 MB peak. Mitigations are designed in: the render is queued and cached, never run on a period change, and — critically — nothing about the preview, the builder, the template, or the browser Print path depends on Chromium at all. The dependency buys the PDF file, not the feature.

Fallback

barryvdh/laravel-dompdf — pure PHP, zero system dependencies

The winner's single realistic failure mode is "this host cannot run Node, Puppeteer and a pinned Chromium" — restricted shared hosting, a locked-down image, a deployment that refuses a 300 MB binary. In that world a Python/Pango toolchain is no more available, so the only viable retreat is the one that needs nothing but PHP.

Dompdf costs fidelity: no flexbox, no grid, no @page margin boxes, and table rows cannot split across pages. This plan pre-pays that cost — the template is deliberately authored with print-safe primitives (semantic tables, block flow, no JS in the document body), so the swap becomes a CSS adjustment rather than a rewrite.

Two escalation paths if even that fidelity proves insufficient, both config-only inside the same package: the WeasyPrint driver (best pure paged-media CSS, needs Python) and the Gotenberg driver (Chromium in its own container, when containers become available).

Implementation plan

Report types, data, template, dependency

Self-contained enough to build from: every period definition, the filter surface, the exact data source, and the template section order.

Report types — one code path, three period definitions

TypePeriod definitionDefault when openedDocument label
Weekly ISO week, Monday–Sunday The last completed week Week 38 · 14–20 September 2026
Monthly Calendar month The last completed month September 2026 (1–30 Sep)
Custom range Explicit from–to, inclusive Today − 30 days → today 15 August – 20 September 2026 (37 days)
  • A partial-period warning appears in the header when the range includes the current, still-open week or month — so a mid-week report is never mistaken for a complete one.
  • Maximum span 366 days, rejected at validation, bounding both the aggregate query cost and a single Chromium render.
  • The period and the active filters are always printed into the document, so a filed or emailed document is self-describing.

Data sources and filters

What exists today
ExportReports streams CSV rows; BuildMonthlyReportSummary computes the full metric set — reported cases, estimated affected hectares, cases by barangay, cases by possible condition, field-validation counts, closed cases, review times, and the expert-verification block.
New payload builder
BuildReportDocument generalises the period handling to an explicit [from, to) range and reuses the existing metric helpers. BuildMonthlyReportSummary stays exactly as it is — it feeds the dashboard and is covered by existing tests, so it delegates rather than changes.
Source of record
Report rows with canonical_report_id null, submitted within the range, filtered through the same ApplyReportFilters and ApplyOperationalQueueFilter actions the CSV export uses — so a report and an export can never disagree about scope.
New queries
Submissions-per-day/per-week bucketing for the trend section, and open/overdue operational queue counts. Both are grouped counts, bounded by the 366-day cap.
Filters in the builder
Period (required), barangay, possible condition, case state, verification outcome, field-validation state, operational queue, and the case-register appendix toggle.
Privacy
The appendix carries farmer_or_farm_owner_name. It is off by default and never emitted unless explicitly enabled, because a period report circulates far more widely than the case register does.

Document template structure

  1. 1
    Masthead
    CaneGuard lockup on the light brand ground, the period as the title, generated-at/by, report reference, and the scope line.
  2. 2
    Decision-support notice
    Operational counts are not population statistics; Possible Condition is not a diagnosis. Present near the top, not buried.
  3. 3
    Key figures
    Submitted reports, estimated affected hectares, requiring field validation, closed cases — with a comparison to the previous equivalent period.
  4. 4
    Submissions over the period
    Per-day (weekly) or per-week (monthly/custom) counts as print-safe inline SVG bars.
  5. 5
    Distribution
    By barangay and by Possible Condition, each with a total row that reconciles.
  6. 6
    Case lifecycle and field validation
    Verification outcomes, case states, and the four field-validation states with the derived requiring-validation count.
  7. 7
    Expert verification feedback
    Consult volume, agreement rate, unable-to-classify rate, time to finding, advisory coverage. Empty denominators are omitted, never shown as zero.
  8. 8
    Operational queues
    Unassigned, needs visit, and overdue against target visit date — the office's action list.
  9. 9
    Case register appendix (opt-in)
    One row per case, the CSV projection, with a repeating header and a continuation note.
  10. 10
    Repeating footer
    CaneGuard, period, page n of total, timezone and generation timestamp, via an @page margin box.
  • Typography: Poppins self-hosted as woff2 (400/600/700) on the API origin — the document CSP is font-src 'self' and the document must render with no network. The SPA's Google Fonts import cannot be reused.
  • Colour: the tokens.css functional greens for headings and rules, the --disease-* tokens for condition rows, warning and danger tokens for overdue and unable-to-verify. Brand mark fills stay in the logo only, matching the deviation already recorded in brand/README.md.
  • Print: A4, @page margin box footer, break-inside: avoid on cards and rows, thead { display: table-header-group } for the appendix.
  • Renderer portability — this is what protects the Dompdf fallback: critical layout uses semantic tables and plain block flow, flex/grid is decorative only, and no JavaScript runs in the document body beyond the print button.

The dependency — one package pair, one npm package, one binary

# API — document rendering and the Chromium driver
composer require spatie/laravel-pdf spatie/browsershot

# Chromium driver runtime (Node is already a documented host prerequisite)
npm install puppeteer

# Host provisioning
#   A pinned Chrome/Chromium binary, with its path set explicitly in config
#   rather than relying on Browsershot autodiscovery.
  • Publish config/laravel-pdf.php with an explicit Chromium path and A4 defaults, so a host upgrade cannot silently change rendering.
  • The render runs queued, never inside the request that also serves the preview — a Chromium render costs seconds and ~250 MB peak.
  • No dependency is needed for the preview, the builder, the template, or the Print path. If Chromium is unavailable, the feature degrades to preview plus browser print — strictly more than exists today.

Validation and testing scope

API — Feature tests
Period resolution for weekly/monthly/custom and their defaults · the 366-day cap and inverted-range rejection · equality with BuildMonthlyReportSummary for a UTC calendar month (the regression test that proves the extraction changed nothing) · authorization mirroring ExpertAuthorizationTest · the HTML route returning the right content type and disposition · empty-period behaviour.
API — CSP regression
The one security-relevant test: the document route emits its route-scoped frame-ancestors value, and every other HTML response still emits frame-ancestors 'none' and X-Frame-Options: DENY. Extends SecurityHeadersTest.
Web — Vitest + RTL + MSW
The builder defaults to the last completed week · exactly one document request per period change (debounce verified with fake timers) · correct parameters per report type · loading, error and empty states · a failed PDF render leaves the preview mounted · the existing CSV export and dashboard panel still pass unchanged.
Fidelity — the real gap
The PDF is produced by Chromium, so no fast test can assert what it looks like. Two mitigations: a document-contract test asserting the rendered HTML contains the required structural markers (footer page-counter rule, repeating thead, every mandatory section, the disclaimer), and a one-time manual PDF verification per template change — pagination, repeated headers, footer page numbers, embedded Poppins, embedded logo.
Commands
npm run lint · npm run typecheck · npm test -- --run · npm run check:api · npm run verify:fast · npm run verify:backend — existing commands only. No E2E, browser or device suites.

Q1 Recommendation: PHT Not queued

Which timezone defines a week and a month?

The existing monthly summary is explicitly UTC-scoped (BuildMonthlyReportSummary: "cases submitted during one UTC calendar month"). Field work, however, is planned on Philippine local days — a Sunday submission sits in different weeks under the two rules. This shifts report counts, so it should be a deliberate choice rather than a side effect.
